# bindgen — the C binding generator

`bindgen` reads a C header and writes an Oskel module of `extern "C"`
declarations, so a C library can be called from Oskel without spelling every
signature by hand. It is a standalone executable: it only transforms text, it
does not link the engine's runtime, and it does not touch the bytecode, the AST
or the VM. The output is an ordinary Oskel module that `oskel` and `oskelc`
already accept.

```sh
bindgen <header.h>                 # write the module to stdout
bindgen <header.h> -o <out.oskl>   # write it to a file
bindgen -                          # read the header from stdin
bindgen --target llp64 <header.h>  # Windows data model (default: lp64)
```

`-h`/`--help` and `-v`/`--version` are also available. Exit codes follow the
toolchain convention: `64` for a usage error, `66` for an unreadable input or an
unwritable output.

## Example

```c
/* str.h */
#include <stddef.h>

typedef unsigned long size_t;

int    strlen(const char *s);
void  *malloc(size_t n);
void   free(void *p);
double sqrt(double x);
int    strcmp(const char *a, const char *b);
```

```sh
bindgen str.h -o str.oskl
```

```oskel
// Generated by bindgen from str.h. Do not edit by hand.
// ...

extern "C" {
  fn strlen(s: cstring): int32;
  fn malloc(n: size_t): ptr;
  fn free(p: ptr): void;
  fn sqrt(x: double): double;
  fn strcmp(a: cstring, b: cstring): int32;
}
```

```oskel
import str;

print(str.strlen("hello"));   // 5
print(str.sqrt(2.0));         // 1.4142135623730951
```

## The C → Oskel type mapping

The generator targets the FFI scalar vocabulary of PHASE 6.6 (see
[language.md](language.md) and `include/ffi_types.h`). A C type is translated
like this:

| C type | Oskel type | Notes |
|--------|------------|-------|
| `char` | `int8` | `unsigned char` is `uint8`; `signed char` is `int8` |
| `short` | `int16` | `unsigned short` is `uint16` |
| `int` | `int32` | `unsigned int` is `uint32` |
| `long` | `int64` on LP64, `int32` on LLP64 | unsigned forms follow |
| `long long` | `int64` | 64-bit on both data models |
| `wchar_t` | `int32` on LP64, `uint16` on LLP64 | follows the C data model |
| `float` | `float` | |
| `double` | `double` | `long double` is skipped |
| `_Bool`, `bool` | `bool` | |
| `void` | `void` | return-only |
| `void *` | `ptr` | any other pointer too |
| `char *` | `cstring` | a NUL-terminated string |
| `signed char *`, `unsigned char *` | `ptr` | a byte buffer, not a string |
| `T[N]`, `T[]` | `ptr` | an array parameter decays |
| `R (*)(P...)` | `fn(P...): R` | a callback parameter (see below) |
| `R (**)(P...)`, `R (*[N])(P...)` | `ptr` | a pointer *to* a callback is opaque |
| `struct S` (by value) | `struct S { ... }` | the body is emitted before the block (see below) |
| `enum E` | `int32` | the members become module constants (see below) |
| `int8_t` … `uint64_t`, `size_t`, `intptr_t`, `uintptr_t`, `ptrdiff_t` | the matching FFI name | recognized without reading `<stdint.h>` |

A `typedef` the header itself declares is resolved, including through pointers,
arrays and function pointers. Qualifiers (`const`, `volatile`, `restrict`),
storage classes (`static`, `extern`, `inline`), attributes
(`__attribute__((...))`, `__declspec(...)`) and calling conventions
(`__stdcall`, `__cdecl`, `WINAPI`, `CALLBACK`, ...) are dropped.

### Callbacks

A C function-pointer parameter becomes a Oskel callback, the `fn(P...): R` the
engine accepts as a parameter (PHASE 6.6). The declarator is written four ways
in C and all four are recognized:

| C | Oskel |
|---|-------|
| `void qsort(..., int (*cmp)(const void *, const void *));` | `cmp: fn(ptr, ptr): int32` |
| `void takes_fn(int cmp(int, int));` (a function *type*) | `cmp: fn(int32, int32): int32` |
| `void takes_fn(int (cmp)(int));` (redundant parentheses) | `cmp: fn(int32): int32` |
| `typedef void (*sighandler_t)(int);` then `sighandler_t h` | `h: fn(int32): void` |

A *pointer* to a callback is not a callback: `int (**pp)(int)`, `int (*arr[4])(int)`
and `cb_t *pcb` are all an opaque `ptr`, because the engine passes them through
without ever calling them.

The engine's vocabulary bounds a callback: it may only be a **parameter** (a
function *returning* a callback is skipped), its parameters must be scalars (a
callback that takes another callback is skipped) and it may not be variadic. A
callback that returns a struct by value is skipped as well.

A callback *parameter* may take a struct by value only if that struct is itself
declarable, for the same reason a function signature may: the layout has to be
known. The engine's callback vocabulary accepts only scalars, so such a
declaration is skipped (the compiler's own reason is quoted).

### Structs

A `struct` used by value is declared as an Oskel `struct` before the
`extern "C"` block, so a signature can spell it:

```c
struct Point { int x; int y; };
struct Point make_point(int x, int y);
```

```oskel
struct Point {
  x: int32;
  y: int32;
}

extern "C" {
  fn make_point(x: int32, y: int32): Point;
}
```

An **anonymous** body is named by its typedef, because that is the only name
the header gives it:

```c
typedef struct { int quot; int rem; } div_t;
div_t div(int num, int denom);
```

```oskel
struct div_t {
  quot: int32;
  rem: int32;
}
```

The layout is validated with `ffi::buildStructLayout`, the same check the
runtime applies, so a body Oskel cannot represent is **never** emitted with a
wrong layout. It is reported instead: a union (overlapping members), an array
field (Oskel fields are whole scalars), a bitfield (intra-struct packing) and a
nested struct (one level only) are all `// skipped:` with the reason that
applies. The emitted `struct` is exactly what a hand-written module would
declare, so nothing about the language changes.

### Object-like macros

An object-like macro whose replacement is a single literal becomes a module
constant:

```c
#define API_VERSION 3
#define MAX_NAME 0x40
#define SCALE 1.5f
#define LIBRARY "mylib"
#define FLAG 'A'
```

```oskel
let API_VERSION = 3;
let MAX_NAME = 64;
let SCALE = 1.5;
let LIBRARY = "mylib";
let FLAG = 65;
```

An integer is emitted as decimal (a C octal `0755` becomes `493`, and a `u`/`l`
suffix is dropped) and must fit the signed 64-bit Oskel integer. A floating
literal loses its `f` suffix; a `long double` is skipped. A string is emitted
only when its escapes are ones Oskel also understands. A character constant is
emitted as its integer code, which is what a C character constant is.

A **function-like** macro (`#define F(x) ...`), a replacement that is an
**expression** (`#define X (A | B)`), a value-less macro (`#define GUARD`) and a
macro whose name is a reserved Oskel keyword are not constants and are ignored.
A macro that collides with a function or a struct keeps the declaration. The
tool does not evaluate the C preprocessor: it only recognizes a literal.

### Enums

A C enum is an `int` at the ABI (BACKLOG §7.10), so a declaration that mentions
one maps to `int32` — the exact spelling, not an approximation. The members
become module constants, which is what lets the program name them:

```c
enum Color { RED, GREEN = 5, BLUE };
enum Color pick_color(int seed);
```

```oskel
let RED = 0;
let GREEN = 5;
let BLUE = 6;

extern "C" {
  fn pick_color(seed: int32): int32;
}
```

The value of a member is a plain decimal, hex or octal literal; a member whose
initializer is a larger expression keeps its position in the sequence (the tool
does not evaluate C constant expressions), so prefer `cc -E` when a header
computes its enum values.

## What is skipped, and why

A declaration the vocabulary cannot express is **not** mis-translated: it is
written as a `// skipped: <name>: <reason>` comment inside the block, and the
count is reported on stderr. Nothing the compiler would reject is ever emitted
as active code. The current skips are:

- a **struct body the Oskel `struct` cannot lay out**: a **union**, an **array
  field**, a **bitfield** or a **nested struct**. A plain struct of scalar
  fields is generated (see above); a pointer to any of these is a `ptr`. An
  **enum** is never skipped: it is an `int` at the ABI.
- a declaration prefixed by a **function-like macro** (`MY_API(int) f(void);`).
  Without a preprocessor the argument may be the return type or mere
  decoration, so the tool reports the declaration instead of guessing. Run the
  header through `cc -E` first to translate it.
- a callback used where the engine does not accept one: **returned** by a
  function (`R (*f(...))(P...)`), **taking another callback**, **variadic**, or
  **returning a struct by value**. A callback *parameter* is generated.
- a signature passing more than **eight register-sized values** (the
  `kMaxExternArgs` bound the FFI thunks enforce). The bound counts *eightbytes*,
  not parameters, so a 16-byte struct spends two of the eight; counting
  parameters would emit a module `oskel -c` refuses. The compiler decides, and
  the tool quotes its message.
- an **anonymous `struct { ... }`** written inline in a signature
  (`int g(struct { int x; } p);`). It has no name to spell, and falling back to
  the empty spelling would pass the struct by value as a scalar `int32`.
- `long double` and any type the tool cannot resolve to the vocabulary.
- a function whose name is a **reserved Oskel keyword** (`for`, `struct`, ...),
  which cannot be a binding name.
- a **function definition** (`static inline ... { ... }`), which has no exported
  symbol to bind.
- a **duplicate** declaration of an already-emitted name.

A **variable** — including a function-pointer variable like `int (*fp)(void);`
— is not a binding and is skipped *without* a comment: it is not a declaration
the vocabulary failed to express, it is simply not a function. Every
*declaration* that names a function is either emitted or reported, never dropped
in silence.

## Variadic functions

A C variadic (`int printf(const char *fmt, ...)`) needs libffi and the System V
AMD64 ABI, and the compiler rejects the declaration outright on a build without
both. `bindgen` therefore writes the real signature **commented out**, so the
module still compiles everywhere and the line is right there to uncomment on a
supporting build:

```oskel
extern "C" {
  // fn printf(fmt: cstring, ...): int32;  // a variadic 'extern "C"' declaration needs libffi and the System V AMD64 ABI, which this build does not have
}
```

The same rule covers **a struct by value** on a build whose marshalling is not
the System V AMD64 ABI (the Microsoft x64 ABI passes a struct through a hidden
pointer, which the register thunks cannot express). The declaration is written
commented out rather than skipped, because the shape *is* in the vocabulary —
only this build cannot carry it:

```oskel
extern "C" {
  // fn make_point(x: int32, y: int32): Point;  // a struct cannot cross the C boundary by value on this target: ...
}
```

The reason after `//` is the compiler's own message, not a second guess: the
tool asks `ffi::validateSignature` twice, once with every ABI capability on
(is the shape in the vocabulary at all?) and once with this build's (can this
build marshal it?). The first answer decides skipped versus commented out, so
the tool cannot drift from the compiler it targets.

## The preprocessor is not run

`bindgen` tokenizes the header as written; it does not evaluate `#include`,
`#ifdef` or `#if`. Preprocessor lines and comments are otherwise ignored, and
both branches of an `#ifdef` are tokenized (a declaration inside a conditional
is usually one you want). The one exception is the literal object-like macro
described above: it is read from the raw source, not expanded into the
declarations. An object-like macro that expands to nothing before a type is
dropped when it is immediately followed by a real type, so the common
`EXPORT int f(void);` still translates. For a header whose macros change the
*type*, preprocess it first and pipe the result in:

```sh
cc -E header.h | bindgen - -o header.oskl
```

## Where the generated bindings run

`extern "C"` is resolved by the **development engine** (`oskel`) through
`Platform::lookupSymbol`, and by the **AOT backend** in `hosted` link mode
(`oskel build --mode hosted`, Linux x86-64 for now). The default AOT mode,
`freestanding`, is a self-contained image with no host: it does not resolve an
`extern "C"` symbol yet (PHASE 7f.5). The generated module is valid in every
case; only the symbol resolution depends on the engine.

The engine resolves **every** symbol of an `extern "C"` block when the module
loads, so the generated module must name symbols the host actually exports. A
wide system header declares things that are not linkable symbols — `alloca` is a
compiler builtin, an `inline`/`static inline` helper has no external definition,
a macro-only name never became a function. Generating from such a header as-is
produces a module that fails at import with `extern "C" symbol '<name>' was not
found in the host`. Trim the header to the library's real exports, or preprocess
it with the right feature macros, before generating:

```sh
cc -E -D_POSIX_C_SOURCE=200809L mylib.h | bindgen - -o mylib.oskl
```

`bindgen` cannot decide this for you: whether a declared symbol is *exported* is
a property of the library, not of the header.

## Building the tool

CMake builds it next to the engine:

```sh
cmake -S . -B build && cmake --build build -j4   # build/bindgen
```

`build.sh` (and `build.bat`) build it too, as `build/bindgen` (and
`build\bindgen.exe`). `cmake --install` puts it in `bin/` beside `oskel`.
